# Calcula UAT Firestore Data Model

This document describes the Cloud Firestore data model used by Calcula UAT v2.0.0.

The web and Android applications share the same Firestore database. The current implementation uses four principal collections:

- `institutions`
- `categories`
- `problems`
- `responses`

The field names documented below correspond to the current implementation.

---

## 1. `institutions`

Stores the institutional configuration used by the current research prototype.

### Fields

| Field | Type | Description |
|---|---|---|
| `scholarKey` | String | Institutional identifier used to associate content and interaction records with an institution. |
| `email` | String | Institutional contact/login email. |
| `institutionName` | String | Name of the participating institution. |
| `password` | String | Password used by the current prototype access mechanism. |
| `academicLevel` | Array | Academic levels enabled for the institution. |

### Academic-level values

The current implementation uses the following internal values:

- `elementary`
- `middle`
- `high`
- `college`

The array may also contain `null` values for levels that are not enabled.

### Example

```json
{
  "scholarKey": "DEMO01",
  "email": "demo@example.edu",
  "institutionName": "Demo Institution",
  "password": "demo-password",
  "academicLevel": [
    "college",
    "high",
    null,
    null
  ]
}
```

> **Security note:** The current prototype stores institutional credentials using a simplified mechanism intended only for controlled research deployments. Real production credentials should not be stored in plaintext. A managed authentication service and stronger access-control policies are recommended for production use.

---

## 2. `categories`

Stores the mathematical categories and subcategories defined by each institution.

### Fields

| Field | Type | Description |
|---|---|---|
| `name` | String | Category name. |
| `subcategories` | Array of Strings | Subcategories associated with the category. |
| `scholarKey` | String | Institutional identifier associated with the category. |

The value `all` is used internally as a general subcategory option.

### Example

```json
{
  "name": "Arithmetic",
  "subcategories": [
    "all",
    "Addition",
    "Subtraction"
  ],
  "scholarKey": "DEMO01"
}
```

---

## 3. `problems`

Stores the mathematical exercises created through the web application.

### Fields

| Field | Type | Description |
|---|---|---|
| `scholarKey` | String | Institutional identifier that owns the problem. |
| `title` | String | Short title of the mathematical exercise. |
| `paragraph` | String | Problem statement. |
| `category` | String | Category assigned to the problem. |
| `subcategory` | String | Subcategory assigned to the problem. |
| `difficulty` | String | Difficulty level. |
| `academicLevel` | String | Academic level associated with the problem. |
| `answers` | Array of Strings | Four possible answers displayed by the mobile application. |
| `solution` | String | Identifier of the correct answer. |

### Difficulty values

The current implementation supports:

- `easy`
- `normal`
- `hard`
- `expert`

### Academic-level values

The current implementation supports:

- `elementary`
- `middle`
- `high`
- `college`

### Example

```json
{
  "scholarKey": "DEMO01",
  "title": "Basic addition",
  "paragraph": "What is 25 + 17?",
  "category": "Arithmetic",
  "subcategory": "Addition",
  "difficulty": "easy",
  "academicLevel": "elementary",
  "answers": [
    "40",
    "41",
    "42",
    "43"
  ],
  "solution": "2"
}
```

The Firestore document identifier is not stored as a field inside the document. When the Android client retrieves a problem, the document ID is added temporarily to the local object as `uid`.

---

## 4. `responses`

Stores interaction records generated by the Android application after a problem is completed correctly.

### Fields

| Field | Type | Description |
|---|---|---|
| `scholarKey` | String | Institutional identifier. |
| `problemId` | String | Firestore document ID of the completed problem. |
| `attemps` | Integer | Number of attempts required to reach the correct answer. |
| `elapsedTime` | Integer | Elapsed response time in seconds. |
| `date` | Map | Date on which the interaction occurred. |

### `date` structure

```json
{
  "day": 8,
  "month": 10,
  "year": 2026
}
```

### Example response document

```json
{
  "scholarKey": "DEMO01",
  "problemId": "exampleFirestoreDocumentId",
  "attemps": 2,
  "elapsedTime": 18,
  "date": {
    "day": 8,
    "month": 10,
    "year": 2026
  }
}
```

> **Implementation note:** The field name `attemps` is retained in version 2.0.0 for compatibility with the current mobile and web implementations. It represents the number of attempts and may be renamed to `attempts` in a future version through a controlled schema migration.

---

## Relationships between collections

The principal logical relationships are:

```text
institutions.scholarKey
        |
        +---- categories.scholarKey
        |
        +---- problems.scholarKey
        |
        +---- responses.scholarKey
```

A response also refers to the problem that generated it through:

```text
responses.problemId
        |
        +---- Firestore document ID of a document in `problems`
```

This organization allows multiple institutions to maintain differentiated educational content while using the same Firestore database.

## Typical data flow

```text
Web application
    |
    | creates / updates
    v
categories
problems
    |
    | retrieved by
    v
Android application
    |
    | user interaction
    v
responses
    |
    | retrieved by
    v
Web analytics interface
```

The web application manages educational content. The Android application retrieves problems according to institution, academic level, category, subcategory, and difficulty.

After a problem is solved, the Android application stores an interaction record in `responses`. The web application subsequently reads those records to produce descriptive learning-analytics indicators.

---

## Offline behavior

The Android client uses Cloud Firestore local persistence.

Previously retrieved content may remain available during intermittent connectivity. Writes generated while offline can be stored locally by the Firestore client and synchronized when connectivity becomes available again.

The software does not implement a separate custom synchronization server.
